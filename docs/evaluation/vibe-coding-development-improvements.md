# バイブコーディングによる開発手法の課題と改善提案

## 継続すべき点

- 最初にMVPの範囲と使用技術を決め、小さく実装を開始したこと
- ユーザーが実際に操作し、押しにくさや文字化けを具体的に報告したこと
- フィードバックを短い周期で実装へ反映したこと
- Git、GitHub Pages、PWAまで含めて、他の端末で利用できる状態にしたこと
- 教材データと進捗データを再利用して、復習や単語テストへ拡張したこと
- 重要な方針をMarkdownやADRとして残し始めたこと

## 優先課題

### 1. ビルド成功だけでは動作の正しさを保証できない

#### 現状

多くの変更で `npm run build` の成功を確認している。これは型エラーやビルドエラーの検出には有効だが、アプリの振る舞いや教材内容の正しさまでは保証しない。

実際に、ビルド成功後もスマートフォンで母音記号の文字化けが発生し、表示方式を複数回修正している。

#### リスク

- 正誤判定や苦手判定の誤りを見逃す
- 進捗データの保存、更新、初期化が想定外に動作する
- 問題や選択肢に重複、不足、偏りが発生する
- PWA更新時に古いキャッシュが残る
- 特定のOS、画面幅、フォントだけで表示が崩れる

#### 改善策

- 正誤判定、進捗保存、問題生成などの単体テストを追加する
- 主要な学習フローの結合テストを追加する
- 対象端末と画面幅を決め、実機確認表を作る
- 完了条件を「型チェック、lint、テスト、ビルド、実機確認」とする
- 不具合修正時は、可能なら再発防止テストも追加する

#### 完了の目安

主要ロジックが自動テストされ、変更ごとに共通の検証チェックリストが実行されている。

### 2. 教材データの正確性をAIの出力だけに依存している

#### 現状

子音分類、母音、発音、独自ローマ字表記、単語の読みなどが追加されているが、教材データの出典、採用基準、レビュー結果が十分に残っていない。ASDoQ評価でも、表記基準、教材データの出典、単語選定基準の不足が指摘されている。

#### リスク

- 誤った発音や分類を利用者に覚えさせる
- 同じ音を画面ごとに異なる記法で表示する
- 後から正誤を確認できず、AIの回答を再検証できない
- 表記変更の影響がカード、一覧、クイズ、単語へ波及する

#### 改善策

- 教材データの出典と確認日を記録する
- 独自ローマ字、IPA、声調、母音表示の規則を一か所に定義する
- データ項目に出典またはレビュー状態を持たせることを検討する
- タイ語話者、教師、辞書など、AI以外の根拠によるレビューを行う
- 教材データの変更を通常のUI変更と分けてレビューする

#### 完了の目安

すべての教材データについて、採用した表記規則と確認可能な根拠があり、重要項目が人または信頼できる資料でレビューされている。

### 3. 自然言語の要望から直接実装へ進み、受け入れ条件が不足している

#### 現状

「押しやすくする」「母音をすべて追加する」「単語テストを作る」といった要望から、短時間で実装へ進んでいる。速度は高いが、対象範囲や完了の判断が実装時の解釈に依存しやすい。

#### リスク

- ユーザーとAIで「完成」の意味が異なる
- 実装後の確認で要件漏れが見つかり、手戻りが増える
- 「すべて」「使いやすい」などの曖昧な表現が残る
- 対象外の機能まで実装してスコープが拡大する

#### 改善策

実装前に、各変更について次の項目を短く記録する。

```text
目的:
対象ユーザー・利用場面:
受け入れ条件:
対象外:
確認方法:
```

小さな修正では対話中の箇条書きでよい。大きな機能ではIssue、仕様書または計画文書へ残す。

#### 完了の目安

実装前に完了条件が確認でき、実装後の報告がその条件に対応している。

### 4. 変更単位が大きく、要求と実装の対応を追跡しにくい

#### 現状

初回MVPコミットには、MVP基盤に加えて子音・母音の拡張、一覧、習得済み表示、複数のUI修正が含まれている。対話には変更経緯があるものの、Git履歴だけでは個々の要求と変更理由を追いにくい。

#### リスク

- 不具合が入った変更を特定しにくい
- 一部の変更だけを戻すことが難しい
- 将来の担当者が変更理由を理解できない
- 対話ログを読まないと仕様の経緯が分からない

#### 改善策

- 原則として、一つの機能または一つの修正を一コミットにする
- コミットメッセージに変更の種類と目的を書く
- 教材、UI、リファクタリングを可能な限り別コミットにする
- 大きな変更は、要求または決定文書への参照を残す

例:

```text
feat: add vowel learning cards
fix: keep quiz controls visible on small screens
docs: define romanization rules
test: verify progress persistence
```

#### 完了の目安

Git履歴だけでも、何をなぜ変更したかをおおむね追跡できる。

### 5. 機能追加に対して学習導線と情報設計の整理が後追いになっている

#### 現状

カード、クイズ、一覧、進捗、復習、苦手リスト、単語テストが順次追加されている。各機能には価値があるが、機能が増えるにつれてタブや画面が詰まり始めている。ASDoQ評価でも、PWA対応時点でUIがやや詰まり始めていることが指摘されている。

#### リスク

- 初学者が次に何をすべきか分からない
- 機能一覧が学習体験の中心になってしまう
- 同じ目的を持つ画面や操作が重複する
- スマートフォンでナビゲーションが複雑になる

#### 改善策

- 初見学習から復習、単語読解までの学習導線を定義する
- 「追加できる機能」ではなく「学習上の次の障害」で優先順位を決める
- 主要な利用者を想定したユーザビリティテストを行う
- 学習効果を確認する指標を決める

想定する基本導線:

```text
文字を知る → カードで覚える → 小テストで確認する → 苦手を復習する
                                      ↓
                                  単語を読む
```

#### 完了の目安

初めて利用する人が、説明を受けなくても次の学習行動を選べる。

### 6. 対話ログと引き継ぎ文書の役割を分ける必要がある

#### 現状

対話ログは証跡として完全性が高いが、収録件数が多く、現在の仕様や未解決事項を把握するために毎回読み直すのは難しい。作業中メッセージも多く、最終的な決定と途中案を区別する必要がある。

#### リスク

- 古い方針を現在の仕様と誤認する
- 新しいセッションや別のPCで必要な情報を探すのに時間がかかる
- 重要な未解決事項が長いログに埋もれる
- 対話を保存しただけで文書化が完了したと考えてしまう

#### 改善策

対話ログは証跡として保存し、日常の開発では次の要約文書を参照する。

- 現在の仕様
- 重要な決定と理由
- 表記ルール
- 既知の制約と不具合
- 未解決事項と次の作業
- 検証済みの環境

同じ内容を複数の文書へ重複して書かず、正本となる文書を決めてリンクする。

#### 完了の目安

対話全文を読まなくても、新しいセッションまたは別の開発者が現在の状態と次の作業を理解できる。

### 7. PWA公開後の更新と互換性の運用が未整備である

#### 現状

GitHub PagesとPWAによって利用可能な状態になった一方、スマートフォンで更新が反映されない場合の案内や、キャッシュの扱いが対話上の個別対応になっている。

#### リスク

- 利用者が古い教材や不具合のある画面を使い続ける
- 保存済み進捗の形式変更によってデータが読めなくなる
- 公開後の不具合を再現できない

#### 改善策

- アプリのバージョンを画面または診断情報で確認可能にする
- Service Workerの更新方針を文書化する
- `localStorage` のデータ形式にバージョンを持たせる
- データ移行と初期化の方針を決める
- 公開前後のスモークテストを定型化する

#### 完了の目安

利用中のバージョンを識別でき、アプリ更新と保存データ変更の手順が再現可能になっている。

## 改善の優先順位

| 優先度 | 対応 | 理由 |
|---|---|---|
| 1 | 教材データの出典、表記規則、レビューを整える | 学習内容の誤りは利用者への影響が最も大きい |
| 2 | 受け入れ条件と共通検証チェックリストを導入する | 手戻りと解釈違いを減らせる |
| 3 | 正誤判定、進捗保存、問題生成の自動テストを追加する | 機能追加時の回帰を防げる |
| 4 | 現在仕様、既知の課題、次の作業を要約する | 対話ログへの依存を減らせる |
| 5 | 学習導線とナビゲーションを見直す | 機能増加による複雑化を抑えられる |
| 6 | コミットを小さくし、変更理由を残す | 問題の特定と引き継ぎが容易になる |
| 7 | PWA更新と保存データの互換性方針を整える | 公開後の安定運用につながる |

## 推奨する開発サイクル

今後は、一つの変更を次のサイクルで進める。

1. 要望の目的、受け入れ条件、対象外を記録する
2. AIが影響範囲、実装案、懸念点を提示する
3. 小さな単位で実装する
4. 型チェック、lint、自動テスト、ビルドを実行する
5. 対象端末で主要な操作とタイ文字表示を確認する
6. 教材変更の場合は出典と表記規則を確認する
7. 仕様、決定、既知の課題を更新する
8. 一つの目的に対応した単位でコミットする
9. 公開後にバージョンと主要機能を確認する

## 最初に導入する最小セット

すべてを一度に整備する必要はない。まず次の三つを導入する。

1. 表記ルールと教材出典を記録する文書
2. 変更ごとの受け入れ条件と検証チェックリスト
3. 現在の仕様、既知の課題、次の作業をまとめた引き継ぎ文書

その後、正誤判定と進捗保存から自動テストを追加し、学習導線とPWA更新方針を整備する。

## 結論

これまでのバイブコーディングは、構想を短期間で利用可能なアプリへ変える点で成果を上げた。今後も対話と実機フィードバックの速さは維持すべきである。

ただし、次の段階ではAIへの依頼をそのまま実装単位にせず、受け入れ条件、検証、教材の根拠、変更履歴を間に置く必要がある。これにより、開発速度を大きく落とさず、正確性、保守性、再現性を高められる。
